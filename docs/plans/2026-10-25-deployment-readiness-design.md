# 部署体检与运行状态设计

## 目标

让零基础用户在部署前回答三个问题：历史数据是否可读、AI 配置是否完整、通知和定时器是否已经达到无人值守运行条件。同时让远程健康接口显示不敏感的运行模式，便于确认服务器实际加载了哪套配置。

## 方案比较

### 方案一：只扩展 `/api/health`

优点是远程查看方便；缺点是服务必须先成功启动，而且不适合检查运行目录写权限等启动前问题。

### 方案二：只增加 `doctor` 命令

优点是部署前即可检查；缺点是服务运行后无法通过监控确认调度器和 AI 模式。

### 方案三：部署体检命令 + 非敏感健康状态 + Docker 时区保障

同时覆盖部署前、运行中和容器环境差异。实现量适中，不引入数据库或第三方 Python 依赖。本项目采用此方案。

## 命令设计

```bash
python main.py doctor
python main.py doctor --deployment
```

- 普通模式检查数据、运行目录、AI 配置、通知配置、调度表达式和时区。
- `--deployment` 要求至少配置一个通知渠道；如果 `AI_ENABLED` 没有开启，则也判定为未达到本项目当前的 AI 部署目标。
- 命令不访问模型、不更新开奖、不发送消息。
- 输出只包含布尔状态、期号、记录数、模型名、通知渠道 ID、调度时间和安全错误摘要。
- API Key、通知 Token、Base URL 和完整异常对象不得输出。

## 健康接口

`GET /api/health` 增加：

- `ai_enabled`
- `ai_required`
- `scheduler_enabled`

不返回 API Key、Token、Base URL、通知接收人或模型请求内容。

## Docker 时区

在镜像中安装 `tzdata`。否则部分精简 Linux 镜像没有 IANA 时区数据库，`ZoneInfo("Asia/Shanghai")` 可能导致调度器启动失败。

## 验证

- 测试普通体检、部署体检成功与失败、无敏感值输出。
- 测试健康接口包含注入的非敏感运行状态。
- 运行完整测试、Python 编译、Compose 配置和差异检查。
